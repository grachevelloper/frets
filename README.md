# Лады · frets

Бэкенд личной библиотеки Guitar Pro. В этой версии API принимает файлы,
сохраняет закладки на такты и проверяет доступ владельца. Интерфейс и AlphaTab
подключаются отдельно.

## Локальный запуск

1. Установите Docker с Compose и запустите Docker.
2. Скопируйте настройки и запустите сервисы.

   ```sh
   cp .env.example .env
   docker compose up --build -d
   ```

   Docker собирает Go-сервисы из исходников. Для компиляции используются
   зависимости из `backend/vendor/`. При первом запуске Docker скачивает базовые образы,
   а Alpine устанавливает корневые сертификаты.

3. API доступен на [localhost:6666](http://localhost:6666/api/v1/me).
   До входа запрос профиля возвращает `401`. Для проверки без ключей OAuth
   используйте локальный профиль.

   ```sh
   curl -i -c /tmp/frets-cookies -X POST \
     -H 'Origin: http://localhost:6666' \
     http://localhost:6666/api/v1/auth/local
   curl -b /tmp/frets-cookies http://localhost:6666/api/v1/songs
   ```

   При первом входе список песен пуст. Файл загружается через `POST /api/v1/songs`,
   а закладка «Припев» на такты 9–12 сохраняется через
   `PUT /api/v1/songs/{songId}/fragments/{fragmentId}`. Пример всей цепочки есть
   в `scripts/smoke.py`.

### Яндекс ID и Google

Укажите ID и секрет приложения в `.env`. Для Яндекса включите доступ к
`login:info` и `login:email`, затем зарегистрируйте точный Redirect URI
`http://localhost:6666/api/v1/auth/callback/yandex`. Вход начинается по адресу
`http://localhost:6666/api/v1/auth/login/yandex`.

Для Google зарегистрируйте `http://localhost:6666/api/v1/auth/callback/google`
и откройте `http://localhost:6666/api/v1/auth/login/google`. После изменения
настроек выполните `docker compose up -d`. Успешный вход выдаёт cookie сессии
и перенаправляет на `/` или переданный маршрут песни. Пока отдельный интерфейс
не подключён, результат входа проверяется через `GET /api/v1/me`.

## Проверки

Для локальных Go-проверок нужен Go 1.27.3 или новее. Docker использует Go 1.27.3.

```sh
cd backend
go test ./...
go vet ./...
cd ..
python3 scripts/smoke.py
```

Дымовой тест использует включённый локальный вход, проверяет байты загрузки,
идемпотентность (повтор запроса с тем же ключом), закладки и удаление.
Тест загружает искусственные байты, чтобы проверить границу ответственности API.

Для тестов репозиториев запустите Compose, затем передайте
`FRETS_TEST_AUTH_DATABASE_URL` и `FRETS_TEST_LIBRARY_DATABASE_URL` с адресами
тестовой PostgreSQL и рабочими ролями сервисов. Схемы должны быть уже
созданы при запуске сервисов. Без этих переменных выполняются остальные
Go-тесты. Подключение к PostgreSQL внутри Compose доступно из сети проекта.

Если тестовое окружение доступно на другом порту, задайте его адрес через
`FRETS_ORIGIN` для `scripts/smoke.py` или `FRETS_E2E_ORIGIN` для Go-тестов.
Значение заголовка Origin можно задать отдельно: `FRETS_PUBLIC_ORIGIN` для
smoke и `FRETS_E2E_PUBLIC_ORIGIN` для Go. Оно должно совпадать с `PUBLIC_ORIGIN`
сервисов. Это позволяет проверять отдельный Compose-проект без остановки
основного локального окружения.

Для сквозных Go-тестов задайте `FRETS_E2E_ORIGIN=http://localhost:6666`
и выполните `go test ./tests/e2e` из backend. Проверки остановки сервисов
включаются отдельно через `FRETS_E2E_COMPOSE_PROJECT` с именем тестового
Compose-проекта. Они временно останавливают auth и перезапускают song-library.
Используйте отдельный тестовый проект со стандартными именами сервисов и
базой `frets`: проверка восстановления читает состояние песни через `psql`
в контейнере postgres. При дополнительных Compose-файлах передайте их через
`COMPOSE_FILE`, а нужный Docker-контекст — через `DOCKER_CONTEXT`.
Для теста версионности миграций задайте `FRETS_TEST_POSTGRES_DATABASE_URL`
с правом создания и удаления отдельной тестовой схемы.

При изменении зависимостей Go обновите их копии командой `cd backend && go mod vendor`
и включите изменения в `backend/vendor/` в тот же коммит, что и `go.mod` и `go.sum`.

## Размещение

Для публичного адреса задайте `PUBLIC_ORIGIN=https://...`, отключите
`LOCAL_LOGIN`, установите HTTPS перед Nginx и задайте отдельный случайный
`INTERNAL_SECRET` для обоих сервисов. Зарегистрируйте Redirect URI на публичном
адресе. API-контейнеры и PostgreSQL должны быть в закрытой сети. Для внутреннего
запроса через другую сеть задайте `AUTH_URL` с HTTPS и ограничьте сетевой доступ
к auth.

Для отдельной базы задайте `AUTH_DATABASE_URL` и `LIBRARY_DATABASE_URL` и
создайте роли и схемы по примеру `deploy/postgres/init-roles.sh`. В PostgreSQL URL
кодируйте спецсимволы пароля. Для файлов задайте `S3_ENDPOINT` (хост и порт),
`S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` и при необходимости `S3_REGION`,
`S3_SESSION_TOKEN`. Подготовьте закрытый бакет с правами на чтение, запись и
удаление объектов. Для физического удаления используйте бакет без версионирования
или настройте удаление старых версий. Локальные пароли из примера предназначены
для запуска на своей машине.
