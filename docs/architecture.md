# Архитектура API

Nginx принимает запросы на порту 6666 локально и передаёт только публичные
маршруты Go-сервисам. `auth` управляет профилями и сессиями. `song-library`
сверяет сессию в `auth` и использует полученный UUID в запросах к библиотеке.
Файлы доступны только через проверку владельца.

## Пакеты Go

- `services/auth/cmd/auth` собирает сервис входа. Пакет `account` управляет
  одноразовыми попытками входа и сессиями. Пакет `oauth` обменивает код на
  профиль Яндекса или Google.
- `services/song-library/cmd/song-library` собирает сервис библиотеки.
  Пакет `library` определяет порядок резервирования, записи и публикации песни.
  Пакеты `files` и `authclient` подключают хранилище и проверку сессий.
- В каждом сервисе `httpapi` читает запросы и формирует HTTP-ответы, а
  `postgres` выполняет запросы и транзакции. Интерфейсы хранилищ определены
  рядом с кодом, который их вызывает. Точки запуска связывают реализации.

## Данные

- `auth.users` хранит UUID, имя, необязательную почту и дату создания.
  `auth.identities` связывает профиль с парой «провайдер + ID аккаунта».
  Совпадающая почта допустима. `auth.sessions` хранит хеш токена, владельца,
  срок действия и время отзыва. `auth.login_attempts` хранит хеши state и
  привязки к браузеру, данные PKCE и срок действия. Callback удаляет запись
  атомарно, поэтому состояние входа можно использовать один раз.
- `song_library.songs` хранит UUID, владельца, заголовок, дату, состояние,
  ключ повторного запроса, SHA-256, размер и ключ исходника после публикации.
  `song_library.upload_attempts` хранит отдельный ключ объекта для каждой
  попытки. Публикация возможна только для активной попытки с действующим сроком.
- `song_library.fragments` хранит UUID, песню, имя и включительные границы.
  Индекс по `song_id` ускоряет чтение и удаление закладок. PostgreSQL проверяет
  `1 ≤ start_bar ≤ end_bar`. Читаемость файла и верхнюю границу проверяет
  клиент при загрузке и открытии.

У каждого сервиса своя рабочая роль и встроенная начальная миграция
`schema.sql`. Связи между схемами хранят UUID без общего внешнего ключа.

## Публичные маршруты

Префикс `/api/v1`. JSON использует camelCase. Ошибка имеет форму
`{"code":"..."}`. Изменяющим запросам нужен заголовок `Origin`, совпадающий
с `PUBLIC_ORIGIN`.

| Метод и путь | Результат |
| --- | --- |
| GET /auth/login/{provider} | 302 на OAuth. Допустимы `yandex` и `google`. Необязательный `next` возвращает к маршруту песни. |
| GET /auth/callback/{provider} | Одноразовая проверка состояния, обмен кода с PKCE, профиль провайдера, cookie и 302. |
| POST /auth/local | 204 и cookie локального профиля. Доступен только при `LOCAL_LOGIN=true` и локальном origin. |
| GET /me | 200 с `id`, `nickname`, `email`, `createdAt`. |
| POST /auth/logout | 204, отзыв сессии и очистка cookie. |
| GET /songs | 200 со списком песен. Поля `id`, `title`, `createdAt`. |
| POST /songs | Multipart `title`, `sha256`, `file` и заголовок `Idempotency-Key`. Максимум 16 МиБ. 201 при создании и 200 при повторе. |
| GET /songs/{songId} | 200 с песней и массивом `fragments`. |
| GET /songs/{songId}/file | 200 с исходными байтами и `Cache-Control: no-store`. |
| PUT /songs/{songId}/fragments/{fragmentId} | UUID задаёт клиент. JSON `title`, `startBar`, `endBar`. 201 при создании, 200 при совпадающем повторе, 409 при конфликте. |
| DELETE /songs/{songId} | 202 при незавершённом удалении, 204 после завершения, включая повтор. |

Фрагмент содержит `id`, `songId`, `title`, `startBar`, `endBar`.
Отсутствующий или чужой ресурс даёт `404 not_found`. Сессия, которую нельзя
использовать, даёт `401 unauthorized`, а ошибка зависимости или таймаут —
`503 unavailable`. `409 upload_conflict` означает несовпадение параметров,
`409 upload_in_progress` — активную попытку, `409 upload_expired` — истёкший
срок. В последних двух случаях повторите отправку с тем же ключом.

Закрытый `POST /internal/sessions/validate` получает cookie сессии и
проверяет `Authorization: Bearer …` по общему секрету. При успехе возвращает
`{"userId":"…"}`. HTTPS-режим включает атрибуты cookie Secure, HttpOnly
и SameSite=Lax.

## Восстановление и перенос

1. При загрузке сервис проверяет SHA-256, резервирует песню и регистрирует
   попытку до записи исходника. Файл получает ключ попытки. После записи
   транзакция переводит песню в `ready` и закрепляет ключ файла.
2. Уборщик удаляет просроченные попытки из хранилища и перепроверяет их ключи.
   Записи попыток сохраняются, чтобы находить файлы, появившиеся после таймаута.
3. При удалении статус `deleting` сразу скрывает песню. После удаления
   файла транзакция очищает фрагменты и оставляет запись `deleted`.
   Если процесс остановился, фоновая проверка возобновляет операцию.

Для переноса остановите оба Go-сервиса и дождитесь завершения внешних
записей в хранилище. Сделайте дамп `pg_dump -Fc --schema=auth
--schema=song_library`. Подготовьте рабочие роли на новой базе и восстановите
дамп в пустую базу через `pg_restore`, сохранив владельцев схем. Скопируйте
файлы под прежними `file_key`. Сверьте SHA-256 готовых исходников со
значениями `songs.sha256`. Запустите сервисы и по ранее сохранённым UUID
проверьте получение песни, фрагмента в её карточке и исходных байтов.
