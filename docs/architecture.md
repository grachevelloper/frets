# Архитектура API

Nginx принимает запросы на порту 6666 локально и передаёт только публичные
маршруты Go-сервисам. `auth` управляет профилями и сессиями. `song-library`
сверяет сессию в `auth` и использует полученный UUID в запросах к библиотеке.
Файлы доступны только через проверку владельца.

## Пакеты Go

Go-модуль находится в backend. Каждый сервис содержит domain с моделями и
правилами, usecase со сценариями, delivery с HTTP и фоновыми обработчиками,
infrastructure с реализациями PostgreSQL и внешних клиентов.
App создаёт зависимости, cmd запускает приложение.
Фоновый worker вызывает продолжение удаления в usecase/song и очистку попыток
в usecase/upload. Первый запрос и продолжение удаления используют одну реализацию.
Очистка попыток и продолжение удаления запускаются независимо: медленное
хранилище при удалении не задерживает очистку загрузок. В продолжении удаления
отдельный срок задан для чтения списка и для каждой песни, чтобы старые сбои
не блокировали новые удаления.
Правила изменения кода описаны в [AGENTS.md](../AGENTS.md).

Общие пакеты находятся в backend/lib. У каждого сервиса отдельные SQL-файлы
в migrations и таблица schema_migrations в собственной схеме. Общий механизм
применяет их транзакционно и проверяет контрольные суммы и наличие ранее применённых файлов.
Начальная миграция совместима с базой предыдущей версии через IF NOT EXISTS.

## Данные

- `auth.users` хранит UUID, имя, почту и дату создания. Новые записи требуют email; старые записи без почты
  сохраняются до повторного входа, их сессии возвращают 401.
  `auth.identities` связывает профиль с парой «провайдер + ID аккаунта».
  Совпадающая почта допустима. `auth.sessions` хранит хеш токена, владельца,
  срок действия и время отзыва. `auth.login_attempts` хранит хеши state и
  привязки к браузеру, данные PKCE и срок действия. Callback удаляет запись
  атомарно, поэтому состояние входа можно использовать один раз.
- `song_library.songs` хранит UUID, владельца, заголовок, дату, состояние,
  ключ повторного запроса, SHA-256, размер и ключ исходника после публикации.
  `song_library.upload_attempts` хранит отдельный ключ объекта для каждой
  попытки. Публикация возможна только для активной попытки с действующим сроком.
- `song_library.fragments` хранит UUID, песню, имя и включительные границы.
  Индекс по `song_id` ускоряет чтение и удаление закладок. PostgreSQL проверяет
  `1 ≤ start_bar ≤ end_bar`. Читаемость файла и верхнюю границу проверяет
  клиент при загрузке и открытии.

У каждого сервиса своя рабочая роль и встроенные SQL-миграции
в каталоге `migrations`. Связи между схемами хранят UUID без общего внешнего ключа.

## Восстановление и перенос

1. При загрузке сервис проверяет SHA-256, резервирует песню и регистрирует
   попытку до записи исходника. Файл получает ключ попытки. После записи
   транзакция переводит песню в `ready` и закрепляет ключ файла.
2. Уборщик удаляет просроченные попытки из хранилища и перепроверяет их ключи.
   Записи попыток сохраняются, чтобы находить файлы, появившиеся после таймаута.
3. При удалении статус `deleting` сразу скрывает песню. После удаления
   файла транзакция очищает фрагменты и оставляет запись `deleted`.
   Если процесс остановился, фоновая проверка возобновляет операцию.

Для переноса остановите оба Go-сервиса и дождитесь завершения внешних
записей в хранилище. Сделайте дамп `pg_dump -Fc --schema=auth
--schema=song_library`. Подготовьте рабочие роли на новой базе и восстановите
дамп в пустую базу через `pg_restore`, сохранив владельцев схем. Скопируйте
файлы под прежними `file_key`. Сверьте SHA-256 готовых исходников со
значениями `songs.sha256`. Запустите сервисы и по ранее сохранённым UUID
проверьте получение песни, фрагмента в её карточке и исходных байтов.
