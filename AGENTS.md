# Работа с frets

## Назначение проекта

frets — личная библиотека Guitar Pro с сохранением фрагментов для занятий.

- auth управляет входом через Яндекс ID и Google, профилями и сессиями.
- song-library управляет песнями, исходниками, фрагментами, загрузкой
  и восстановлением после сбоев.

Основной сценарий — войти, загрузить песню, сохранить такты 9–12
как «Припев» и позднее открыть фрагмент по сохранённой ссылке.

Локальный адрес — http://localhost:6666.
Redirect URI Яндекса — http://localhost:6666/api/v1/auth/callback/yandex.

## Структура

- backend содержит один Go-модуль, оба сервиса и общие пакеты.
- backend/services/<service>/cmd содержит точку запуска сервиса.
- backend/services/<service>/internal содержит его реализацию.
- backend/services/<service>/migrations содержит SQL-миграции сервиса.
- backend/lib содержит общие технические пакеты.
- backend/tests/e2e содержит проверки работающей системы через API.
- deploy содержит Dockerfile, Nginx и подготовку PostgreSQL.
- docs содержит архитектуру, API и эксплуатацию.
- README.md содержит инструкции запуска и проверки.

При переносе файлов обновляй импорты, Docker, команды проверок и документацию.

## Слои

### domain

Сущности, состояния и правила предметной области. Здесь проверяются
допустимые данные и переходы состояний.

Domain не зависит от HTTP, PostgreSQL, OAuth-клиентов, хранилища файлов
и других слоёв приложения. Группируй связанные сущности в содержательные
пакеты. Методы и конструкторы должны обеспечивать реальные правила.

### usecase

Сценарии приложения и порядок операций. Например, загрузка проверяет
контрольную сумму, резервирует попытку, записывает исходник и публикует песню.

Usecase зависит от domain и интерфейсов необходимых операций.
Определяй интерфейс рядом с потребителем и включай только используемые методы.
Именуй входные параметры и результаты методов интерфейса по их назначению.
HTTP-статусы, JSON-теги, SQL и конкретные внешние клиенты принадлежат внешним слоям.

### delivery

HTTP-обработчики, маршруты, промежуточные обработчики и запуск фоновых сценариев.

HTTP-обработчик читает запрос, вызывает сценарий, преобразует результат
и записывает ответ. Форматы HTTP-запросов и ответов определены здесь.

Используй константы net/http для статусов и методов. Явно преобразуй ошибки
в стабильные публичные коды. Внутренний текст ошибки не становится code ответа.

Фоновый обработчик управляет расписанием и отменой. Правила восстановления
принадлежат соответствующим сценариям usecase. Продолжение удаления находится
рядом с удалением песни, очистка попыток — рядом с загрузкой.

### infrastructure

PostgreSQL, OAuth, файловая система, S3 и клиент другого сервиса.
Здесь находятся SQL, транзакции и преобразования ошибок внешних систем.
Реализации выполняют интерфейсы потребителей.

### app и cmd

App читает настройки, создаёт зависимости и управляет их жизненным циклом.
Cmd запускает приложение и обрабатывает завершение процесса.
Загружай настройки явно и передавай зависимости через конструкторы.
Завершение процесса выполняется в точке запуска.

## Общие пакеты

Выноси код в backend/lib при фактическом использовании несколькими сервисами.
У каждого пакета должно быть конкретное назначение.

- httpjson записывает JSON-ответы.
- httpserver настраивает и корректно останавливает HTTP-сервер.
- httpmiddleware содержит общую проверку Origin публичных запросов.
- postgres открывает соединения и применяет переданные миграции.

Модели и бизнес-правила остаются внутри сервисов. Сервисы взаимодействуют
через API и не импортируют internal друг друга.

## PostgreSQL и транзакции

Одна PostgreSQL, отдельные схемы, роли, SQL-миграции и история миграций
для каждого сервиса. Механизм применения миграций общий.
Применённые SQL-файлы изменяются следующей миграцией.

Границы атомарных операций выражай в интерфейсах репозитория.
Транзакции и типы драйвера остаются в infrastructure/postgres.
Domain задаёт правила. SQL-условия и ограничения обеспечивают их
при одновременных запросах.

## Гарантии поведения

### Вход

- Профиль определяется парой «провайдер + ID аккаунта».
- Совпадающая почта не объединяет профили.
- Попытка входа привязана к браузеру, имеет срок и используется один раз.
- OAuth использует state и PKCE.
- Секреты сессий и привязки входа хранятся в базе в виде хешей.
- Истёкшие и отозванные сессии закрывают доступ.

### Песни

- Любая операция проверяет владельца.
- Чужой и отсутствующий ресурс имеют одинаковый публичный ответ.
- Исходник готовой песни неизменяем.
- Песня и попытка резервируются до записи файла.
- Каждая попытка получает отдельный ключ файла.
- Публикация разрешена только текущей действующей попытке.
- Повтор загрузки с прежним ключом сохраняет результат операции.
- Просроченные ключи перепроверяются для удаления поздно появившихся файлов.

### Удаление

- Состояние deleting сразу закрывает доступ к песне.
- Отсутствующий файл считается удалённым.
- Очистка фрагментов и завершение удаления выполняются атомарно.
- Повтор удаления продолжает ту же операцию.
- После перезапуска фоновые сценарии возобновляют незавершённую работу.

### Ошибки и данные

- Недействительная сессия возвращает 401.
- Сбой или таймаут auth возвращает 503.
- Названия песен и фрагментов сохраняются в исходном виде.
- JSON использует camelCase и стабильные коды ошибок.

## Тестирование

Тесты находятся рядом с проверяемым кодом и разделены по ответственности.

- Domain проверяется тестами правил, границ и состояний.
- Usecase проверяется тестами сценариев с подменой внешних зависимостей.
- Delivery проверяется запросами и ответами через httptest.
- Репозитории проверяются с настоящей тестовой PostgreSQL.
- Внешние клиенты проверяются на корректные запросы и обработку сбоев.
- E2E проверяет пользовательские цепочки через работающий API.

Приоритетны права доступа, целостность данных, повторные и одновременные
запросы, отмена и восстановление. Выноси сложные тестовые данные и таблицы
случаев в именованные переменные. Общие тестовые помощники добавляй при повторении.

## Проверки

Из backend запускай применимые проверки.

- go test ./...
- go vet ./...

При изменении репозиториев запускай тесты с PostgreSQL.
При изменении запуска или API проверяй Docker Compose и затронутые
сквозные сценарии на localhost:6666.

Изменяя зависимости, обновляй go.mod, go.sum и vendor. Компиляция Go
в Docker использует vendor и проходит без доступа к сети.

Перед передачей результата просмотри полный diff и связанные файлы.
Проверь границы пакетов, названия, ошибки и отсутствие посторонних изменений.
Сообщай о выполненных проверках и ограничениях.
